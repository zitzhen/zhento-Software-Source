# Contributing to zhento-Software-Source

Thanks for your interest in improving this project. This repository is the source
of truth for the apt repository published at `https://apt.zitzhen.cn`. It lists
upstream GitHub projects in `Software.list`; a manually triggered GitHub Actions
workflow builds `amd64` `.deb` packages from them, signs the apt indexes, and
syncs everything to Cloudflare R2.

Contributions are welcome: adding packages, improving the build/publish scripts,
fixing documentation, and reporting issues are all useful. This guide explains
the conventions you need to follow.

## Ways to contribute

- **Add a package** by appending an upstream repository URL to `Software.list`.
- **Improve tooling** in `scripts/` or the workflow in `.github/workflows/`.
- **Improve documentation** in `README.md` or this guide.
- **Report bugs or request packages** by opening an issue with the upstream URL
  and, for bugs, the relevant logs and your environment details.

## Development setup

The scripts target a Debian/Ubuntu environment (the workflow runs on
`ubuntu-latest`), so use a compatible machine or container for local checks.
Install the needed tools:

```bash
sudo apt-get update
sudo apt-get install -y git devscripts equivs dpkg-dev gnupg apt-utils
```

Enable the versioned Git hooks after cloning. Every commit must carry a
`Signed-off-by` trailer (Developer Certificate of Origin); the hooks add and
verify it automatically:

```bash
git config core.hooksPath .githooks
```

Make sure `user.name` and `user.email` are configured, since the hooks use them
for the sign-off:

```bash
git config user.name "Your Name"
git config user.email "you@example.com"
```

If you do not use the hooks, you can sign commits manually with `git commit -s`.
Commits without a valid sign-off are rejected by the `commit-msg` hook.

## Adding a package

1. Create a branch for your change.
2. Append one `https://github.com/<owner>/<repo>` URL to `Software.list`.
3. Validate the manifest locally (see below).
4. Commit with a DCO sign-off and open a pull request describing the package.

`Software.list` rules, enforced by `scripts/parse-software-list.sh`:

- One HTTPS GitHub repository URL per line, e.g.
  `https://github.com/zitzhen/patchsplit`.
- An optional trailing `.git` or `/` is accepted and normalized.
- Blank lines and lines starting with `#` are ignored; inline `#` comments are
  stripped.
- Duplicate URLs are ignored (a warning is printed).
- The list must contain at least one entry.
- The upstream repository **must** contain a `debian/` directory with valid
  Debian packaging metadata, and the build must produce an `amd64` `.deb`.
  Check this on the upstream repository before submitting a PR.
- Preserve the license header and maintainer block at the top of the file.

Packages are not published by a pull request alone. After a change is merged, a
maintainer runs the **Publish apt repository to R2** workflow manually from the
Actions tab.

## Local validation

Validate the manifest and, when changing the build pipeline, try a local build:

```bash
./scripts/parse-software-list.sh Software.list
./scripts/build-deb.sh https://github.com/zitzhen/patchsplit /tmp/debs
```

The parse script prints the JSON build matrix and fails on invalid or empty
input. The build script clones the upstream repo, installs its build
dependencies with `mk-build-deps` (which requires `sudo`), and runs
`dpkg-buildpackage -b -us -uc`; it fails if no `amd64` package is produced.

Check shell syntax for any script you modify:

```bash
bash -n scripts/*.sh .githooks/*
```

To test publishing metadata end to end you need a signing key available to GPG;
`scripts/publish-repo.sh` expects an artifacts directory, an output directory,
and a key ID. Do not export or commit the repository's private signing key.

## Commit and pull request guidelines

- Keep each pull request focused on one logical change.
- Explain **why** the change is needed, reference any related issue, and note how
  you validated it (which commands you ran).
- All commits must include the DCO `Signed-off-by` trailer.
- Only edit source files: `dists/`, `pool/`, `Packages`, `Release`, `InRelease`,
  and similar metadata are generated by the workflow and must not be committed.
- Do not modify the GPG key ID or repository URL defaults without discussing the
  change first; clients rely on the published fingerprint `3B310141DFDBDE77A802C0627DFBD414F81DC0BB`.
- Never include secrets in code, logs, or pull requests. R2 credentials, the GPG
  private key, and its passphrase belong exclusively in the repository's GitHub
  Actions secrets.

## Review and merge

A maintainer reviews pull requests for correctness of the package metadata,
compliance with the manifest rules, and clean build results. Once approved and
merged, publishing happens through the manually triggered workflow described in
`README.md`.
